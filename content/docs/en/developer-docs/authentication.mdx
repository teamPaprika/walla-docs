# Authentication

The Walla Open API authenticates requests with an API key or an OAuth access token. Every API request must include one of them in a request header. OAuth tokens can be used only for certain read operations and for downloading response files.

## Choosing an authentication method

| Item | API key | OAuth access token |
|------|---------|--------------------|
| Header | `X-WALLA-API-KEY: <API key>` | `Authorization: Bearer <access token>` |
| Team scope | The team the key was issued for (no team needs to be specified) | Teams the token user belongs to. `GET /workspaces` and `GET /forms` require `teamId` ([Specifying a team](#specifying-a-team)) |
| Available operations | All Open API operations | Read operations and response file downloads only ([Scopes and allowed operations](#scopes-and-allowed-operations)) |
| Permissions | Permissions tied to the API key | The token user's team membership, workspace access, response viewing and file download permissions |
| Rate limit | 6,000 requests per hour per API key | Hourly per-team quota based on the plan ([OAuth token call quota](#oauth-token-call-quota)) |
| Best for | Team-level server integrations; response search, export, delivery and write operations | Apps that read data within a user's permissions |

If you send both headers, the API key takes precedence. Existing API key integrations keep working exactly as before.

## API Key Authentication

To authenticate your API requests, you need to include your API key in the `X-WALLA-API-KEY` header.

### Header Format

```
X-WALLA-API-KEY: your_api_key_here
```

### Team-Scoped API Keys

API keys in Walla are created at the **team level**. This means:

- Each API key is associated with a specific team
- The team context is automatically included with every API request
- You don't need to provide team information in your API calls
- All workspaces, forms, and responses you access are automatically filtered by your team

## Obtaining Your API Key

To get your API key:

1. Log in to your Walla account at [app.walla.my](https://app.walla.my)
2. Navigate to [app.walla.my/open-api/doc](https://app.walla.my/open-api/doc)
3. Find the API key section at the top of the page
4. Generate or copy your API key

> **Important**: Keep your API key secure and never share it publicly. Treat it like a password.

## Making Authenticated Requests

Here are examples of how to include your API key in different programming languages:

### cURL

```bash
curl -X GET "https://api.walla.my/open-api/v1/workspaces" \
  -H "X-WALLA-API-KEY: your_api_key_here" \
  -H "Content-Type: application/json"
```

### JavaScript (Fetch)

```javascript
fetch('https://api.walla.my/open-api/v1/workspaces', {
  method: 'GET',
  headers: {
    'X-WALLA-API-KEY': 'your_api_key_here',
    'Content-Type': 'application/json'
  }
})
  .then(response => response.json())
  .then(data => console.log(data))
  .catch(error => console.error('Error:', error));
```

### Python (requests)

```python
import requests

url = "https://api.walla.my/open-api/v1/workspaces"
headers = {
    "X-WALLA-API-KEY": "your_api_key_here",
    "Content-Type": "application/json"
}

response = requests.get(url, headers=headers)
data = response.json()
print(data)
```

### Node.js (axios)

```javascript
const axios = require('axios');

const config = {
  headers: {
    'X-WALLA-API-KEY': 'your_api_key_here',
    'Content-Type': 'application/json'
  }
};

axios.get('https://api.walla.my/open-api/v1/workspaces', config)
  .then(response => console.log(response.data))
  .catch(error => console.error('Error:', error));
```

## OAuth access tokens

Send an OAuth access token in the `Authorization: Bearer <access token>` header. Paths and response formats are the same as for API key calls, but only the operations in the table below can be called.

### Getting a token

Tokens are obtained through the OAuth authorization code flow. Follow these rules when requesting one:

- Always request the `openid` scope. Without it, every call returns `401`, and refreshing the token does not fix it.
- Request the scopes that match the operations you need (`project:read`, `project:response.read`, `project:response.download`).
- To refresh tokens, also request `offline_access`. Without it, no refresh token is issued.
- Do not send the `resource` parameter (RFC 8707). If you do, every call made with that token returns `403 insufficient_scope`.

In some deployments (for example, on-premises), issuing and refreshing new tokens may be disabled. Even then, tokens that were already issued remain usable until they expire or are revoked.

### Scopes and allowed operations

Paths are relative to `/open-api/v1`.

| Scope | Allowed operations |
|-------|--------------------|
| `project:read` | `GET /teams`<br />`GET /workspaces`, `GET /workspaces/{workspaceId}`, `GET /workspaces/{workspaceId}/forms`<br />`GET /forms`, `GET /forms/{formId}`<br />`GET /forms/{formId}/fields`, `GET /forms/{formId}/fields/{fieldId}`, `GET /forms/{formId}/fields/{fieldId}/description`<br />`GET /forms/{formId}/hidden-fields`<br />`POST /forms/{formId}/exports/field-definitions`<br />`GET /field-output-schemas` |
| `project:response.read` | `GET /forms/{formId}/responses` |
| `project:response.download` | `POST /forms/{formId}/responses/{responseId}/fields/{fieldId}/file` ([Download a response file](/en/docs/developer-docs/responses#download-a-response-file)) |

**API key-only operations**: Calling the following operations with an OAuth token returns `403 This endpoint does not accept OAuth tokens`.

- Get a specific response `GET /forms/{formId}/responses/{responseId}`
- Search responses `POST /forms/{formId}/responses/search`
- Export responses `POST /forms/{formId}/exports/responses`
- Form delivery (all operations under `/forms/{formId}/delivery`)
- Add (`POST`) or delete (`DELETE`) hidden fields

### Specifying a team

When you call `GET /workspaces` or `GET /forms` with an OAuth token, the `teamId` query parameter is required. Without it, the call returns `400`. API key calls ignore `teamId`.

Look up team IDs with [`GET /teams`](/en/docs/developer-docs/workspaces#list-teams). With a token, it returns only the teams the token user belongs to that pass the team's Open API setting and IP access restrictions.

```json
{
  "success": true,
  "data": [
    { "id": "team_456", "name": "Marketing Team", "profileUrl": null }
  ]
}
```

- A guest who has not turned on two-factor authentication still sees the team in the list, but operations on that team return `403`.
- When you call `GET /workspaces/{workspaceId}` with a token and the token user cannot access that workspace, the call returns `403 {"error":"Access denied"}`.

### cURL examples

The examples below assume you have stored an already-issued access token in the `WALLA_OAUTH_TOKEN` environment variable.

```bash
# 1. List callable teams (project:read)
curl -X GET "https://api.walla.my/open-api/v1/teams" \
  -H "Authorization: Bearer $WALLA_OAUTH_TOKEN"

# 2. List a team's workspaces (project:read, teamId required)
curl -X GET "https://api.walla.my/open-api/v1/workspaces?teamId=team_456" \
  -H "Authorization: Bearer $WALLA_OAUTH_TOKEN"

# 3. List form responses (project:response.read)
curl -X GET "https://api.walla.my/open-api/v1/forms/form_abc/responses" \
  -H "Authorization: Bearer $WALLA_OAUTH_TOKEN"
```

For a response file download example, see [Download a response file](/en/docs/developer-docs/responses#download-a-response-file).

## Authentication Errors

If authentication fails, the API will return one of the following error responses:

### 401 Unauthorized

This error occurs when:
- The API key is missing from the request
- The API key is invalid, expired, or revoked

**Response Example:**

```json
{
  "error": "Unauthorized"
}
```

### 403 Forbidden

Authentication succeeded, but you don't have permission to access the requested resource.

**Response Example:**

```json
{
  "error": "Forbidden"
}
```

### OAuth token errors

- **401**: The token is invalid or expired. The response includes the `WWW-Authenticate: Bearer error="invalid_token"` header. This is the only case in which you should refresh the token.
- **403 `insufficient_scope`**: The token lacks a required scope. The body is `{"error":"insufficient_scope","scope":"<required scope>"}`.
- **403 `This endpoint does not accept OAuth tokens`**: This is an [API key-only operation](#scopes-and-allowed-operations). Call it with an API key.
- **403 `Forbidden`**: The user is not a team member, is a guest without two-factor authentication, or used a workspace ID they cannot access.
- **403 `Unauthorized`**: The server could not verify the token. This does not mean the token is invalid, so do not refresh it; try again shortly.

For the full list of errors, see [Error Codes](/en/docs/developer-docs/error-codes).

## Best Practices

### Security

- **Never commit API keys** to version control systems (Git, SVN, etc.)
- **Use environment variables** to store API keys in your application
- **Rotate keys regularly** for enhanced security
- **Use different keys** for development, staging, and production environments

### Environment Variables

Store your API key in environment variables:

```bash
# .env file
WALLA_API_KEY=your_api_key_here
```

Then access it in your code:

```javascript
// JavaScript
const apiKey = process.env.WALLA_API_KEY;
```

```python
# Python
import os
api_key = os.getenv('WALLA_API_KEY')
```

### Rate Limiting

The Walla Open API enforces rate limits to ensure fair usage and system stability:

- **Rate Limit**: 6000 requests per hour per API key
- **Time Window**: 1 hour (rolling window)

If you exceed the rate limit, the API will return a `429 Too Many Requests` response. When this happens:

- Implement exponential backoff for retries
- Cache responses when appropriate
- Avoid making unnecessary duplicate requests
- Monitor your API usage to stay within limits
- Consider batching operations where possible

The limit above applies to API key calls.

#### OAuth token call quota

OAuth token calls are counted separately from the API key limit of 6,000 requests per hour and are available on every plan. The plan sets only the quota. A team's quota is shared by all users and apps in that team.

| Applies to | Hourly quota |
|------------|--------------|
| Free plan teams | 600 requests |
| Pro plan teams | 3,000 requests |
| Enterprise and custom plan teams | 6,000 requests |
| `GET /teams`, `GET /field-output-schemas` | 600 requests per user |

- The 1-hour window starts with the team's (or user's) first call.
- When the quota is exceeded, the API returns `429 {"error":"rate_limit_exceeded"}` with the `Retry-After` (seconds), `RateLimit-Limit`, `RateLimit-Remaining` and `RateLimit-Reset` headers. Wait for `Retry-After` before retrying.
- Calls sent after the quota is exceeded still count.
- The team's Open API setting and IP access restrictions apply regardless of plan.

## Troubleshooting

### Common Issues

**Problem**: Getting 401 errors despite using the API key

**Solutions**:
- Verify the API key is correct and hasn't expired
- Check that you have the necessary permissions for the workspace
- Ensure the header name is exactly `X-WALLA-API-KEY` (case-sensitive)
- Verify you're accessing resources within your authorized workspaces

**Problem**: API key not being sent

**Solutions**:
- Check that the header is properly formatted
- Ensure your HTTP client is including custom headers
- Verify there are no typos in the header name

**Problem**: Calling `GET /workspaces` or `GET /forms` with an OAuth token returns a 400 error

**Solutions**:
- Include the `teamId` query parameter. You can find team IDs with `GET /teams`

**Problem**: An OAuth token call returns a 403 error

**Solutions**:
- For `insufficient_scope`, check that you requested the required scope and did not send the `resource` parameter in the token request
- For `This endpoint does not accept OAuth tokens`, call the endpoint with an API key
- For `Unauthorized`, do not refresh the token; try again shortly

## Additional Security Considerations

### Protecting Your API Key

1. **Don't hardcode it**
   - Never put an API key directly in your source code
   - Use environment variables or a secret management service

2. **Use HTTPS only**
   - The API is reachable over HTTPS only
   - HTTP requests are rejected

3. **Monitor for exposure**
   - Regularly check that keys haven't been pushed to public repositories
   - If a key is exposed, revoke it immediately and issue a new one

### Managing Permissions

- API keys are tied to workspace permissions
- Issue a separate API key per team member
- Revoke unused keys right away
- Review API key usage periodically
- OAuth token calls are subject to the token user's team membership, workspace access, and response viewing and file download permissions

### Error Handling Best Practices

```javascript
async function makeAuthenticatedRequest(url) {
  try {
    const response = await fetch(url, {
      headers: {
        'X-WALLA-API-KEY': process.env.WALLA_API_KEY,
        'Content-Type': 'application/json'
      }
    });

    if (response.status === 401) {
      console.error('Authentication failed: check your API key');
      // Notify the user or start a re-authentication flow
      return null;
    }

    if (!response.ok) {
      throw new Error(`HTTP error! Status: ${response.status}`);
    }

    return await response.json();
  } catch (error) {
    console.error('Request failed:', error);
    throw error;
  }
}
```

```python
import requests
import os

def make_authenticated_request(url):
    headers = {
        'X-WALLA-API-KEY': os.getenv('WALLA_API_KEY'),
        'Content-Type': 'application/json'
    }

    try:
        response = requests.get(url, headers=headers)

        if response.status_code == 401:
            print('Authentication failed: check your API key')
            return None

        response.raise_for_status()
        return response.json()

    except requests.RequestException as e:
        print(f'Request failed: {e}')
        raise
```
