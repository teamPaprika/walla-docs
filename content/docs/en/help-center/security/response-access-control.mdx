Even among members participating in the same form project, you may need each member to **view only the responses they are responsible for**—based on region, department, score range, and more. With Response Access Control on the **Enterprise plan**, you can control each project's response viewing scope—for example, showing only `Region = Seoul` responses to a Seoul regional researcher while hiding Gyeonggi and Busan responses.

Response access control is applied in **two steps**:

1. **Workspace role level**: In **Workspace Settings → Roles & Permissions**, turn off **View all responses** for the target role and select **Follow project settings**.
2. **Project level**: In the form editor, go to **Form Settings → Project permissions → Response access**, choose **Do not allow**, **All responses**, or **Matching responses** for that role, and click **Save**.

## Walkthrough: Setup and Restricted View

Follow these steps to configure conditional response access and see what a restricted member sees:

<Steps>
  <Step>
    ### Delegate response viewing at the workspace role level

    In **Workspace Settings → Roles & Permissions**, set the target workspace role's **View all responses** permission to **Follow project settings**.
  </Step>
  <Step>
    ### Select Matching responses in Form Settings

    In the form editor, open **Form Settings → Project permissions → Response access** and select **Matching responses** for that role.
  </Step>
  <Step>
    ### Add and save condition rules

    Add and save condition rules (for example, `Region = Seoul`) to define which responses the role can access.
  </Step>
  <Step>
    ### Verify the restricted Response Sheet view

    When a restricted member opens the **Response Sheet**, a banner reading **"Only responses you can access are shown."** appears at the top, and only matching response rows are displayed.
  </Step>
  <Step>
    ### Verify the restricted Analytics view

    When a restricted member opens **Analytics**, a restriction notice appears explaining that visit and behavior analytics are unavailable and directing them to **Response Statistics** instead.
  </Step>
</Steps>

## How to Write Condition Rules

When you select **Matching responses**, you can combine **rules** and **conditions**.

- **Conditions (AND)**: Adding multiple conditions within a single rule allows only responses that satisfy **all conditions simultaneously**. *(Example: `Region includes any of [Seoul]` **AND** `Overall satisfaction ≥ 4`)*
- **Rules (OR)**: Adding another rule with **Add rule** allows responses that satisfy **any one of the rules**.
- **Supported field types**: You can filter by `Submitted at`, choice fields (Multiple Choice, Dropdown, Linear Scale, etc.), Short Text, Number, Date fields, and more.

<Callout type="warn" title="Warning">
Immediately after changing **View all responses** to **Follow project settings** on a workspace role, members in that role cannot view any responses until a rule is saved on each individual form (**Do not allow** state). Be sure to save **All responses** or **Matching responses** under **Form Settings → Project permissions → Response access** for each form.
</Callout>

## Behavior in Results and Management Views

When a member with restricted response access opens a project's results views, each feature behaves as follows:

| Feature Area | Behavior |
| --- | --- |
| **Response Sheet** | Shows the banner **"Only responses you can access are shown."** at the top and displays only rows that meet the allowed conditions. *(If 0 accessible responses match the current search or filter, "No accessible responses match the current filter." is shown.)* |
| **Individual Responses · Response Statistics** | Only accessible responses are aggregated and displayed, so hidden response counts and raw answers are never exposed. |
| **Download · Delete Responses** | Even if the member has download or delete permissions, they can only export or delete accessible responses. *(Downloading is disabled if 0 responses are accessible.)* |
| **Analytics (Visit & Behavior Analysis)** | To prevent overall traffic metrics such as views and drop-off rates from being separated from the accessible response set, **visit and behavior analytics are not provided.** *(A top banner directs users to Response Statistics.)* |
| **Moving a Project to Another Workspace** | Moving a form to another workspace **deletes all response access rules tied to the previous workspace's roles**. You must reconfigure the rules in the new workspace after moving. |

<Callout type="info" title="Good to know">
Saving a response access policy **takes effect immediately regardless of whether the form is republished**. However, condition fields are chosen from already-published form fields—if you add a new field, publish the form first before selecting it in a condition rule.
</Callout>
